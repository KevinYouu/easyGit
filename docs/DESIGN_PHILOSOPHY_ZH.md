# easyGit 设计哲学

## 核心定位

easyGit 是一个 **Git 工作流增强工具**,而不是 Git 命令的替代品。

### 我们的使命

**整合复杂、难记忆的 Git 工作流,让 Git 使用更简单、更高效。**

## 设计原则

### ✅ 应该做什么

#### 1. 整合多步骤工作流

将需要多个命令组合的复杂工作流整合为单个交互式命令。

**示例:**
```bash
# ❌ 传统方式 - 多步骤,易出错
git add -A
git commit -m "feat: add feature"
git pull --rebase
git push

# ✅ easyGit 方式 - 一条命令,交互式引导
easyGit push-all
# 引导: 选择提交类型 → 输入消息 → 自动 add + commit + pull + push
```

#### 2. 简化难记忆的命令

为那些参数复杂、难以记忆的 Git 命令提供友好的交互式界面。

**示例:**
```bash
# ❌ 传统方式 - 参数复杂,难记忆
git tag -a v1.2.3 -m "Release v1.2.3"
git push origin v1.2.3

# ✅ easyGit 方式 - 交互式,无需记忆
easyGit tag
# 引导: 输入版本号 → 选择前缀/后缀 → 自动创建并推送
```

#### 3. 提供可视化和引导

通过 TUI 界面提供可视化反馈和操作引导,降低学习曲线。

**示例:**
```bash
# ✅ 交互式 rebase 引导
easyGit rebase-interactive
# 显示提交列表,可视化选择操作(pick/squash/edit)

# ✅ 冲突解决助手
easyGit resolve-conflicts
# 显示冲突文件,引导选择解决策略
```

#### 4. 优化重复性工作

为频繁的批量操作提供高效工具。

**示例:**
```bash
# ✅ 批量分支清理
easyGit batch-cleanup
# 自动检测已合并分支,批量删除

# ✅ 批量标签管理
easyGit tag-delete
# 多选删除,批量操作
```

### ❌ 不应该做什么

#### 1. 不重复 Git 原生的简单命令

如果 Git 原生命令已经足够简单,我们就不应该重新实现。

**反例:**
```bash
# ❌ 不需要实现
easyGit switch branch-name
# 原因: git switch 已经足够简单

# ❌ 不需要实现
easyGit stash
# 原因: git stash 已经足够简单

# ❌ 不需要实现
easyGit log
# 原因: git log 已经很好用
```

#### 2. 不过度简化,导致失去灵活性

过度简化会让用户失去对 Git 的理解和控制。

**反例:**
```bash
# ❌ 不应该实现
easyGit quick-push -m "message"
# 问题: 跳过了重要的确认步骤,用户不知道发生了什么
# 可能导致: 意外提交、强制推送等问题
```

#### 3. 不实现所有 Git 功能

我们是 Git 的补充,不是替代品。用户仍需要学习 Git 基础。

**正确态度:**
- ✅ 用 easyGit 处理复杂工作流
- ✅ 用 git 命令处理简单操作
- ✅ 两者结合,互补使用

## 功能分类指南

### 应该实现的命令类型

#### 🟢 A类: 多步骤工作流

**特征:**
- 需要 3+ 个命令组合
- 有固定的执行顺序
- 经常一起使用

**示例:**
- ✅ `push-all` - add + commit + pull + push
- ✅ `push-selected` - 选择性 add + commit + push
- ✅ `release` - version bump + tag + push + changelog
- ✅ `tag` (带推送) - tag + push tag

#### 🟡 B类: 参数复杂命令

**特征:**
- 参数多且难记
- 有多种使用模式
- 容易出错

**示例:**
- ✅ `reset` - 交互式选择提交和模式
- ✅ `rebase-interactive` - 可视化 rebase 操作
- ✅ `cherry-pick` - 可视化选择提交
- ✅ `merge` - 引导选择分支和策略

#### 🔵 C类: 批量操作

**特征:**
- 需要重复执行
- 有筛选条件
- 可以优化为批量

**示例:**
- ✅ `tag-delete` - 批量删除标签
- ✅ `branch-delete` - 删除分支(可扩展为批量)
- ✅ `batch-cleanup` - 批量清理已合并分支

#### 🟣 D类: 辅助和增强

**特征:**
- 提供额外价值
- 改善用户体验
- 不改变核心功能

**示例:**
- ✅ `status` - 带颜色的增强状态
- ✅ `set-language` - 语言配置
- ✅ `init` - 引导式仓库初始化

### 不应该实现的命令类型

#### ❌ X类: Git 原生已简单

**特征:**
- 单个命令即可完成
- 参数简单易记
- 无需交互式引导

**示例:**
- ❌ `switch` → 用 `git switch`
- ❌ `stash` → 用 `git stash`
- ❌ `add` → 用 `git add`
- ❌ `commit` → 用 `git commit`
- ❌ `pull` → 用 `git pull`
- ❌ `fetch` → 用 `git fetch`
- ❌ `log` → 用 `git log`
- ❌ `diff` → 用 `git diff`

#### ❌ Y类: 过度简化

**特征:**
- 隐藏了重要细节
- 降低了用户控制
- 可能引发问题

**示例:**
- ❌ `quick-push` → 跳过确认,风险高
- ❌ `auto-merge` → 自动解决冲突,危险
- ❌ `force-push` → 太危险,不应简化

#### ❌ Z类: 边缘功能

**特征:**
- 使用频率极低
- 维护成本高
- 收益不明显

**示例:**
- ❌ `reflog` → 高级功能,很少用
- ❌ `filter-branch` → 复杂场景,保持原样
- ❌ `bisect` → 调试工具,原生足够

## 用户体验原则

### 1. 渐进式复杂度

- 简单操作 → 直接用 Git
- 中等复杂 → 用 easyGit 引导
- 高度复杂 → 学习 Git 高级用法

### 2. 保持可见性

用户应该清楚知道执行了什么操作:
- ✅ 显示每个步骤
- ✅ 展示实际执行的 Git 命令
- ✅ 提供确认机制

### 3. 可中断和可恢复

所有操作都应该:
- ✅ 可以取消 (Ctrl+C, q)
- ✅ 提供撤销建议
- ✅ 不破坏工作区

### 4. 教育性

帮助用户学习 Git:
- ✅ 提示等效的 Git 命令
- ✅ 解释每个步骤的作用
- ✅ 引导到官方文档

## 实现决策流程图

```
新功能提议
    ↓
是否是单个 Git 命令? ──是→ ❌ 不实现,用原生 Git
    ↓ 否
是否需要 3+ 步骤? ──否→ 评估参数复杂度
    ↓ 是              ↓
是否有固定流程? ──是→ ✅ 实现为工作流命令
    ↓ 否              ↓
是否难以记忆? ──否→ ❌ 不实现
    ↓ 是              ↓
是否频繁使用? ──否→ ❌ 不实现
    ↓ 是
✅ 实现为交互式命令
```

## 命令命名规范

### 工作流命令

- `push-all` - 完整推送流程
- `push-selected` - 选择性推送
- `rebase-interactive` - 交互式变基
- `resolve-conflicts` - 冲突解决

### 批量操作命令

- `tag-delete` - 删除标签
- `branch-delete` - 删除分支
- `batch-cleanup` - 批量清理

### 辅助命令

- `set-language` - 设置语言
- `init` - 初始化仓库

### 命名原则

- ✅ 使用动词-名词结构
- ✅ 描述性强,易于理解
- ✅ 与 Git 命名保持一致性
- ❌ 避免与 Git 原生命令冲突

## 总结

### easyGit 的价值在于

1. **整合** - 多步骤工作流的一站式解决方案
2. **引导** - 复杂命令的交互式界面
3. **提效** - 批量操作和智能默认值
4. **增强** - 更好的视觉反馈和用户体验

### easyGit 不是

1. ❌ Git 的完整替代品
2. ❌ Git 学习的捷径
3. ❌ 所有 Git 命令的 TUI 版本

### 给开发者的建议

在考虑添加新功能时,问自己:

1. 这个功能解决了什么痛点?
2. Git 原生方式有多复杂?
3. 我们的方案提供了多少价值?
4. 是否会让用户失去对 Git 的理解?

**记住: 我们是让 Git 更好用,而不是替代 Git。**
